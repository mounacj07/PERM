### 1.2 Process CPU Monitoring Root Cause (`loadgen_cpu_pct = 0.0`)
In `compare_scaling.py`, `loadgen_cpu_pct` was recorded as 0.0 across all runs. Investigation of the execution model revealed the exact structural cause:
1. **Thread vs Process Architecture:** `burst_test.py` dispatches open-loop request load using `concurrent.futures.ThreadPoolExecutor(max_workers=250)`. These worker threads execute *inside the same Python process* as the test runner script (`os.getpid()`), NOT as operating system subprocesses.
2. **Subprocess Misattribution:** `compare_scaling.py` spawned `telemetry_collector.py` as an external subprocess (`server_proc = subprocess.Popen(...)`), but attached `psutil.Process(os.getpid())` to its own process, labeled it `flask_cpu_pct`, and then queried `_flask_psutil.children(recursive=True)` for load-generator child processes.
3. **Result:** Because Python threads have no separate process IDs (PIDs) in the OS process table, `children()` returned an empty list. Consequently:
   - `loadgen_cpu_pct` was recorded as **0.0%**.
   - The CPU consumed by the 250 load generator threads was conflated with runner CPU and recorded under `flask_cpu_pct` (12.8% – 19.9% of machine, or 2.05 – 3.18 thread equivalents).
4. **Correction:** On Windows with thread pools, client load generator CPU cannot be isolated via child process enumeration; it executes within the runner process context.

#### Measured Findings:
1. **Single-Sample Speed Comparison:**
   * Pure Python recursive node traversal (**67.8 $\mu$s**) beats both old flat arrays (**253.1 $\mu$s**) and stacked 2D arrays (**117.6 $\mu$s**) for single-sample inference. This occurs because Python's lightweight pointer dereferencing on small node objects avoids repeated NumPy array slicing and indexing overhead.
   * Flat array representations **only win in batch mode**, where vectorized batch prediction (`predict(X, use_flat=True)`) achieves **90,159.3 samples/second** (>1,000 samples/batch), outperforming single-sample execution loops by over an order of magnitude.
   * The scikit-learn single-row figure (**1,880.9 $\mu$s**) **measures call overhead, not algorithm speed**. Invoking `hgb.predict(x[None, :])` on an isolated single-sample slice incurs extensive Python/Cython array conversion, shape checking, and validation wrappers per call.
2. **Stacked Array Speedup:**
   * Among flat representations, the stacked 2-D array implementation (`predict_one_stacked`) traverses all 50 tree levels simultaneously, reducing single-sample latency from 253.1 $\mu$s to 117.6 $\mu$s (a 2.15$\times$ speedup over sequential flat trees).

## 3. Early-Exit Gating Architecture & Evaluation

### 3.1 Gate Formulation
* **Gate Condition:** Early exit after $K_0$ trees is triggered if and only if:
  $$(\hat{y}_{K_0} + \text{margin} < \text{threshold}) \quad \text{AND} \quad \sum_{i=1}^5 |\Delta_i| < \epsilon$$
  where $\sum_{i=1}^5 |\Delta_i|$ is the sum of **ABSOLUTE changes** over the last 5 trees (fixing previous signed sum cancellation), with $\epsilon = 1.0$ req/s.
* **Overload Threshold Definition:** Arrival rate above which required capacity exceeds the baseline active worker pool:
  $$\text{threshold} = \frac{\text{active\_workers} \times 0.7}{0.126}$$
  - For $\text{active\_workers} = 2$: $\text{threshold} = \frac{2 \times 0.7}{0.126} = \mathbf{11.11\text{ req/s}}$.
  - For $\text{active\_workers} = 8$: $\text{threshold} = \frac{8 \times 0.7}{0.126} = \mathbf{44.44\text{ req/s}}$.

## 5. Known Limitations

1. **Host-Level Contamination:** The load generator threads and telemetry master share CPU with worker processes on a single physical host, causing 2.82 to 4.71 sustained logical threads of non-worker load (peaking up to 7.90 threads), exceeding the 4 logical CPUs reserved for background services.
2. **Process CPU Misattribution on Windows:** Python thread pool workers run inside the runner process; child process polling cannot separate load generation CPU from test execution CPU.
3. **Synthetic Workload Source:** All demand traces were generated via `burst_test.py`; production Locust cluster traffic data is pending.
